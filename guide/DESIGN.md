# WAXFIT 설계 — 진단과 보완

이 문서는 ChatGPT에서 만든 WAXFIT(공유 대화 ‘왁싱샵 프로모션 분석’과 `waxfit-hyunseok…chatgpt.site`)을 검토해, **GitHub로 배포하고 네이버·구글에서 찾을 수 있는 서비스**로 옮기면서 바꾼 설계를 정리합니다.

## 1. 원래 설계 요약 (공유 대화 기준)

| 요청 | ChatGPT 결과 |
|---|---|
| 살롱핏 아이디어를 왁싱샵에 적용, **첫 방문 유인 · 재방문 설계**에만 집중 | 프로모션 선택 화면 + 성과 대시보드 |
| 남녀 구분, 미용실과 다른 방문 주기 | 성별 필터, 개인 방문 주기 |
| AI가 마케팅 트렌드를 계속 학습해 프로모션 아이디어 발전 | 트렌드 자동 갱신 **미연결**로 끝남 |
| 신규 유인·재방문 옵션 목록에서 사장님이 선택, 할인율은 스펙트럼으로 조절 | 할인 조절 + 최소 이익 미달 경고 |
| 효과 검증용 데이터 분석 패키지와 시각화 메뉴 | CSV → 재방문율·공헌이익·고객군 비교, 관찰 기간 미종료 고객 별도 표시, CSV 검증 |
| 베이지·누드(+네이비) 색, 내 고객 데이터 시트 | 색 변경, ‘고객 데이터’ 메뉴, 엑셀 시트(Waxfit_Customer_Data.xlsx) |
| 사업자 노출용 랜딩페이지, 로그인 → 구독 결제, 결제 관리 페이지 | 월 29,000원 단일 요금·포트원 정기결제·카카오/네이버 로그인 **제안 단계에서 ChatGPT 사용량 한도 초과로 중단** |

## 2. 진단 — 검색에 나오지 않고 서비스로 쓰기 어려운 이유

| # | 문제 | 근거 |
|---|---|---|
| 1 | **검색로봇이 사이트를 볼 수 없음** | 사이트 주소가 “Sign in required — Continue with ChatGPT” 로그인 화면(HTTP 401)을 돌려줌. 구글·네이버 로봇은 로그인하지 않으므로 내용이 0 |
| 2 | 주소·코드의 주인이 내가 아님 | `chatgpt.site`는 OpenAI 도메인. 소유 확인·robots.txt·sitemap을 직접 관리할 수 없고, 공유 대화에서도 코드 출력은 가려져 있어 옮길 원본이 없음 |
| 3 | 사장님이 ChatGPT 계정으로 로그인해야 함 | 호스팅이 제공하는 로그인이 ChatGPT 계정 |
| 4 | 결제·로그인 미완성 | 마지막 작업이 사용량 한도로 중단 |
| 5 | 소개 페이지와 앱(손님 기록)이 한곳에 | 공개해야 할 것(소개)과 숨겨야 할 것(손님 데이터)이 섞임 |
| 6 | ‘AI 학습’이 실제로는 연결 안 됨 | 트렌드 자동 갱신 미연결 상태로 데모 데이터만 존재 |
| 7 | 광고성 메시지 수신 동의를 기록만 하고 활용 규칙이 없음 | 재방문 안내는 광고성 정보라 동의·표시 의무가 있음 |
| 8 | 분석 결과의 신뢰도 표시 없음 | 매장 한 곳의 표본은 작아서 프로모션 간 차이가 우연일 수 있음 |

## 3. 바꾼 구조

```
GitHub 저장소 (원본·이력·검토)
  └─ push → GitHub Actions
        ├─ 테스트 · 빌드 · 배포 전 검사 (오류면 중단)
        ├─ GitHub Pages 배포 (HTTPS, 자체 도메인 연결 가능)
        └─ IndexNow 알림 (네이버·Bing)

사이트
  /        소개(랜딩)  ── 공개 · 검색 대상 · 서버 없이 정적 HTML (네이버 로봇도 바로 읽음)
  /app/    데모 앱     ── noindex · 로그인 없음 · 손님 기록은 사용자 브라우저에만 저장
  (2단계)  로그인·구독결제·운영자 결제 관리 ── 서버 필요 → 4장
```

| # | 보완 | 구현 위치 |
|---|---|---|
| 1 | 공개 소개 페이지를 정적 HTML로 분리, 제목·설명·canonical·Open Graph·구조화 데이터 자동 삽입, sitemap·robots 생성, 배포 때 IndexNow | `src/index.html`, `scripts/build.mjs`, `scripts/lib/seo.mjs` |
| 2 | 내 저장소·내 도메인으로 이전, 원본은 git으로 관리 | 저장소 전체, `guide/DEPLOY.md` |
| 3 | 데모는 로그인 없이 바로 체험 → 소개 페이지의 핵심 행동(CTA) | `/app/` |
| 4 | 결제·로그인은 서버가 필요해 2단계로 분리하고 설계만 확정 | 4장 |
| 5 | 앱은 `noindex` + sitemap 제외, 손님 기록은 기기 밖으로 나가지 않음(백업 파일로만 이동) | `src/app/index.html`, `src/app/js/state.js` |
| 6 | ‘AI 학습’ 대신 지금은 **매장 데이터 기반 추천**(아래 5-1)을 정직하게 표시, 트렌드 갱신은 사람 검토를 거치는 2단계 흐름으로 | `economics.js`, 4-4 |
| 7 | 수신 동의한 손님만 안내 대상, 문구에 (광고)·발신 매장·무료 수신거부 자동 포함, 야간 발송 주의 안내 | `src/app/js/views/retention.js` |
| 8 | 관찰 기간이 끝난 손님만으로 재방문율 계산, 95% 신뢰 구간, 표본 30명 미만 경고 | `src/app/js/analytics.js` |
| + | 배포 전 검사: TODO 자리표시·깨진 링크·alt 누락·http 리소스·홈 noindex 등은 배포 차단 | `scripts/check.mjs` |
| + | Pages가 꺼져 있거나 ‘Deploy from a branch’면 실패 대신 설정 방법 안내 | `scripts/ci/pages-status.mjs` |

## 4. 2단계 — 정식 출시 설계 (구독·결제·로그인)

GitHub Pages는 정적 호스팅이라 비밀키 보관, 결제 승인 검증(웹훅), 정기 결제 실행을 할 수 없습니다. 그래서 프런트엔드는 지금처럼 GitHub Pages에 두고, 서버 기능만 서버리스 백엔드로 붙이는 구조를 권합니다.

```
브라우저(GitHub Pages)                  백엔드 (예: Supabase 서울 리전)
  /app 로그인 ── 카카오·네이버 OAuth ──▶  Auth (계정 ↔ 매장)
  결제 버튼 ── 포트원 빌링키 발급 ─────▶  Edge Function: 빌링키로 첫 결제 + 다음 결제 예약
                                         ◀── 포트원 웹훅: 결제 결과 검증 → subscriptions 갱신
  매장 기능 ── 구독 상태 확인 ──────────▶  DB (매장별 행 단위 접근 제어)
  /admin(운영자) ── 결제 관리 ──────────▶  실결제/테스트 구분, 구독 상태, 다음 결제일, 실패·해지·환불
GitHub Actions ── DB 마이그레이션·함수 배포를 같은 저장소에서 자동화
```

### 4-1. 로그인
- 구독한 매장만 기능을 쓰게 하려면 카카오·네이버 로그인 결과(토큰)를 **서버에서 교환·검증**해야 합니다(클라이언트 시크릿 보호, 위조 방지). Supabase Auth는 카카오를 기본 지원하고, 네이버는 Edge Function에서 토큰 교환 후 계정에 연결합니다.
- 필요한 것: 카카오 디벨로퍼스·네이버 개발자센터 앱 등록, 리다이렉트 주소(자체 도메인), 비즈 앱 심사(카카오 이메일 등 동의 항목을 받을 경우)

### 4-2. 구독 결제 (월 29,000원, VAT 포함, 단일 요금)
- 포트원(PortOne) V2 **빌링키** 방식: 브라우저에서 빌링키 발급 → 서버가 빌링키로 결제·다음 결제 예약 → **웹훅으로 결과를 서버에서 검증한 뒤에만** 구독 활성화
- 실제 결제 전 준비: **사업자등록, 통신판매업 신고(대상 여부 확인), PG사 계약**(포트원에서 PG 선택), 이용약관·환불 규정·개인정보처리방침, 사이트 하단 사업자 정보 표시
- 무료 체험 후 유료 전환·요금 인상 시 사전 고지·동의 절차 필요(전자상거래 관련 규정 — 출시 전 전문가 확인 권장)

### 4-3. 손님 데이터를 서버에 둘 때
- 손님 정보의 주인(개인정보처리자)은 각 매장, WAXFIT은 처리를 맡은 수탁자 → 약관에 위탁 내용 명시
- 매장별 행 단위 접근 제어(RLS), 연락처 암호화, 접근 기록, 보관 기간·파기 규칙
- 지금처럼 별칭 중심·연락처 선택 입력 원칙 유지 (모으지 않는 것이 가장 안전)

### 4-4. AI 트렌드 갱신 (사람이 검토하는 흐름)
- GitHub Actions 예약 실행(예: 주 1회) → 생성형 AI API로 프로모션 아이디어·문구 초안 작성 → **Pull Request로 제안** → 운영자가 검토·병합하면 배포
- 자동 반영하지 않는 이유: 과장·부당 광고 문구, 근거 없는 수치가 그대로 사장님께 전달되는 것을 막기 위함
- 필요한 것: AI API 키(저장소 Secrets), 프롬프트·출처 기준

## 5. 앱 계산 규칙

### 5-1. 첫 방문 할인 (스펙트럼)
| 값 | 계산 |
|---|---|
| 첫 방문 공헌이익 | 정가 × (1 − 할인율) − 1회 변동비 |
| 재방문 1회 공헌이익 | 정가 × (1 − 재방문 할인율) − 1회 변동비 |
| 회수에 필요한 재방문율 | 할인액 ÷ 재방문 1회 공헌이익 |
| 손님 1명당 기대 공헌이익 | 첫 방문 공헌이익 + 재방문율 × 재방문 1회 공헌이익 |
| 색 구간 | **위험**: 첫 방문 공헌이익 < 최소 이익 · **주의**: 재방문율 < 회수 필요 재방문율 · **안전**: 그 외 |
| 추천 할인율 | 프로모션의 일반 추천값을 출발점으로, 위 ‘위험·주의’가 되지 않는 최대 할인율을 넘지 않게 낮춤 |
| 재방문율 | 관찰 완료 손님이 20명 이상이면 **내 매장 실제 값**, 아니면 설정의 가정값(기본 40%) |

예) 정가 70,000원, 변동비 20,000원, 할인 20%, 재방문율 40% → 첫 결제 56,000원, 첫 방문 공헌이익 36,000원, 회수 필요 재방문율 28% → 안전

### 5-2. 재방문 시점
- 다음 방문 예정일 = 마지막 방문일 + 주기(손님 개인 주기 → 시술·성별 기본 주기 → 35일)
- 상태: 예정(8일 이상) · 임박(7일 이내) · 지남 · 휴면(주기의 2배 넘게 방문 없음)
- 시술 기본 주기와 가격은 **예시 값**으로 시작하며, 매장 설정에서 바꾸면 ‘예시’ 표시가 사라짐

### 5-3. 성과 분석
- 손님을 **첫 방문 때 받은 프로모션**으로 묶어 비교
- 재방문 = 첫 방문 다음 날부터 관찰 기간(기본 60일) 안에 다시 방문
- 관찰 기간이 끝나지 않은 손님은 ‘관찰 중’으로 따로 세고 재방문율 계산에서 제외
- 공헌이익 = 관찰 기간 안 결제액 − 변동비(방문 기록의 값 → 시술 메뉴 값). 변동비를 모르는 손님은 공헌이익 평균에서 제외하고 개수를 표시
- 95% 윌슨 신뢰 구간, 관찰 완료 30명 미만이면 ‘표본 적음’

### 5-4. CSV 가져오기 검증
- 필수 열: 고객ID·성별·방문일·시술·결제액 (열 이름은 여러 표기를 인식: 예 ‘결제 금액’, ‘방문 날짜’)
- 오류(그 행 건너뜀): 빈 고객ID, 알 수 없는 성별, 잘못된 날짜, 빈·음수·숫자 아닌 결제액, 수신동의 값 오류
- 확인 필요(가져오되 알림): 이미 있는 기록(같은 고객·날짜·시술), 같은 고객의 성별 불일치, 결제액 > 정가, 미래 날짜
- 내보내기: UTF-8 BOM(엑셀 한글 깨짐 방지), 수식 주입 방지(`=`, `+`, `-`, `@`로 시작하는 글자 앞에 `'`)

## 6. 남은 결정 (사장님·운영자가 정할 것)

| 항목 | 필요한 이유 |
|---|---|
| 문의 채널 (카카오톡 채널·이메일 등) | 소개 페이지의 연락 수단 — 지금 비어 있음 |
| 자체 도메인 | 네이버 등록·robots.txt·브랜드 신뢰 |
| ‘왁스핏’ 상표 확인 | 같은 이름의 업체·상표와 충돌 방지 |
| 2단계 백엔드·PG사 선택, 사업자 준비 | 구독 결제 시작 조건 |
| 공식 채널(블로그·인스타그램) | 네이버 브랜드 검색, 구조화 데이터 `sameAs` |
